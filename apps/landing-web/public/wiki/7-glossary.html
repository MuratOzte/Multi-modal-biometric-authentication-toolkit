Purpose and Scope

This page defines core terminology specific to the SecureKit multi-modal biometric authentication toolkit. It details the technical implementation, data flows, configuration parameters, and architectural patterns behind each concept, linking them directly to code entities across the monorepo.

Sources: README.md 1-145 docs/BIOMETRIC_ACCEPTANCE.md 1-139 docs/ASPNET_CUTOVER.md 1-110

1. Parity Stage and Parity Harness

Parity stages (stage-one through stage-seven) represent incremental milestones used during the migration and contractual verification between the legacy Node/Express API (packages/node-auth) and the default ASP.NET Core 10 API (apps/securekit-api). The parity harness (aspnet-parity.mjs and related scripts) executes sequential HTTP contract comparisons against both backend implementations using automated fixtures.

  • Data Flow: The test runner issues identical HTTP payloads across both backend endpoints, recording response structures, status codes, and headers into .run-logs/aspnet-parity.json.
  • Key Functions/Classes: Parity validation runner scripts located in packages/node-auth/scripts/ and C# integration test suites under apps/securekit-api.tests.

Sources: docs/ASPNET_CUTOVER.md 76-102

2. Biometric Manifest

A manifest is a JSON configuration structure (manifest.json) utilized by the biometric acceptance testing framework to declare paths, sample metadata, and verification parameters for face, voice, and card evaluation pipelines without exposing raw personally identifiable information (PII) or embedding vectors to the Git repository.

  • Implementation: Managed via preparation scripts (scripts/biometric-acceptance-prepare.mjs) and validated by the acceptance engine (scripts/biometric-acceptance.mjs).
  • Data Flow: The manifest specifies file locations under .run-logs/acceptance/samples. The runner loads these samples, initializes an isolated temporary C# API instance, and validates HTTP contract responses against predefined success criteria.

Sources: docs/BIOMETRIC_ACCEPTANCE.md 56-128

3. Biometric Preflight

Preflight refers to the environment verification phase executed prior to real biometric acceptance tests (scripts/biometric-preflight.mjs and .py). It checks runtime dependencies, CUDA availability, binary path resolutions, and FFmpeg integration.

  • Implementation: Performs non-destructive dependency checking (e.g., verifying Python imports for FaceNet, Whisper, SpeechBrain, and PaddleOCR) without downloading model weights or parsing raw user images.
  • Key Files: scripts/biometric-preflight.mjs, producing output logs at .run-logs/biometric-preflight.json.

Sources: docs/BIOMETRIC_ACCEPTANCE.md 8-39

4. Model and Hardware Acceptance

Model and hardware acceptance designates the phase of verification where actual deep-learning models (MTCNN, FaceNet, Whisper, SpeechBrain, OpenCLIP, PaddleOCR) and host hardware accelerators (CPU, CUDA GPUs) execute real inference pipelines.

  • Distinction: Unlike protocol fixture tests (apps/securekit-api.tests), which validate JSON serialization and routing contracts, model acceptance evaluates numerical embedding similarity, liveness detection, optical character recognition accuracy, and hardware throughput under constraints defined by FACE_DEVICE, VOICE_DEVICE, and timeout configurations.

Sources: docs/BIOMETRIC_ACCEPTANCE.md NaN-NaN

5. Challenge TTL and Challenge Store

Challenge TTL (Time-To-Live) and the Challenge Store manage time-sensitive, single-use authentication challenges (such as speech verification challenge phrases or cryptographic nonces).

  • Implementation: Challenges are generated server-side, assigned an expiration timestamp (TTL), stored in an in-memory or session-backed repository (ChallengeStore), and invalidated immediately upon verification attempt or timeout.

Sources: README.md NaN-NaN

6. Step-Up Authentication (step_up)

step_up is an intermediary authentication decision outcome generated by the risk evaluation engine when baseline multi-factor signals are insufficient, ambiguous, or indicate elevated risk.

  • Decision Model: The risk engine evaluates aggregated signals (keystroke dynamics, face match score, IP/network reputation) to produce one of three outcomes: allow, step_up, or deny. A step_up result forces the client SDK to prompt for an additional biometric modality (e.g., voice or card verification) before session promotion.

Sources: README.md 13-14

7. Sliding Window Face Reference Management

Sliding window face refers to a reference management strategy for face biometric profiles where historical embedding vectors are dynamically updated or rotated using a rolling window mechanism (FACE_SLIDING_REFERENCES_ROOT).

  • Implementation: Rather than relying strictly on a single static enrollment image, the sliding window approach maintains a bounded set of reference embeddings, accommodating gradual changes in appearance, lighting, or angles over time while bounding storage growth.

Sources: docs/ASPNET_CUTOVER.md 46-47

8. Exponential Moving Average (EMA) Keystroke Profile

An EMA keystroke profile utilizes an Exponential Moving Average algorithm to continuously adapt and update a user's typing rhythm baseline (keydown / keyup hold and flight times) across authentication sessions.

  • Data Flow: Each successful authentication updates the user's keystroke feature vector by blending historical profile weights with the incoming sample measurements via exponential weighting, allowing the system to adapt to natural variations in typing behavior over time.

Sources: README.md 9-10

9. Reference Roots

Reference roots (Face__AllowedReferenceRoots__0, Card__AllowedReferenceRoots__0) are explicit filesystem directory whitelists configured in ASP.NET Core (appsettings.json or environment variables) that restrict where the API can read or write biometric reference images and OCR templates.

  • Security Role: Enforces strict filesystem sandboxing, ensuring that biometric storage paths cannot be manipulated via path-traversal attacks through request payloads.

Sources: docs/ASPNET_CUTOVER.md 57-59

10. Worker Bridge

The worker bridge is the inter-process communication layer where C# verification services invoke isolated Python worker processes (CardPython, FacePython, VoicePython, KeystrokePython) via standard input/output (stdin/stdout) CLI contracts and temporary file exchanges.

  • Data Flow: C# services serialize input payloads or pass temporary file paths to specialized Python worker scripts, enforce strict execution timeouts (VOICE_PYTHON_TIMEOUT_MS, CARD_PYTHON_TIMEOUT_MS), manage process-tree termination, and parse structured JSON responses returned via stdout.
