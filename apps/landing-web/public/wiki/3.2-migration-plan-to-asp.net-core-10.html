Purpose and Scope

The purpose of this document is to define the architectural migration plan for transitioning the legacy Node.js Express API located in packages/node-auth to a modern, high-performance ASP.NET Core 10 API located in apps/securekit-api (net10.0), ensuring complete contract compatibility without modifying client-facing applications MIGRATION_TO_ASPNET10_PLAN.md 1-6

The scope explicitly preserves the following components during the initial transition:

  • The React/Vite demo application (apps/demo-web) MIGRATION_TO_ASPNET10_PLAN.md 8-10
  • The TypeScript web SDK (packages/web-sdk) MIGRATION_TO_ASPNET10_PLAN.md 8-11
  • Python workers for face, voice, card, IP, and fixed-text keystroke validation MIGRATION_TO_ASPNET10_PLAN.md 8-12
  • Existing HTTP routes, request/response payload schemas, and error structures MIGRATION_TO_ASPNET10_PLAN.md 8-13

Python workers are integrated via a controlled process bridge managed directly by C# services MIGRATION_TO_ASPNET10_PLAN.md 15 Database transitions, password security enhancements, and advanced authentication strategy shifts are treated as independent efforts separate from this API compatibility migration MIGRATION_TO_ASPNET10_PLAN.md 16-17

Sources: MIGRATION_TO_ASPNET10_PLAN.md 1-18

The target system is structured around modern .NET 10 conventions utilizing ASP.NET Core Controllers, xUnit testing with WebApplicationFactory, and robust JSON file-based storage adapters that match the legacy Node.js behavioral contracts MIGRATION_TO_ASPNET10_PLAN.md 19-33

Migration Principles and Methodology

The migration adheres to a strict zero-regression rule set, ensuring that the legacy Node API remains operational until the corresponding C# modules pass all validation gates MIGRATION_TO_ASPNET10_PLAN.md 34-42

  1. Fallback Preservation: The Node API (packages/node-auth) is preserved until every C# module passes all test harnesses MIGRATION_TO_ASPNET10_PLAN.md 34-36
  2. Incremental Commits: Every migration step consists of small, independent, and revertible commits MIGRATION_TO_ASPNET10_PLAN.md 37
  3. Contract-First Development: Schemas and tests are established prior to implementation MIGRATION_TO_ASPNET10_PLAN.md 38
  4. Strict Parity: Routes, HTTP methods, status codes, and JSON field definitions remain unaltered MIGRATION_TO_ASPNET10_PLAN.md 39
  5. Dual-Run Validation: Identical endpoints are executed against both Node and C# environments to verify payload parity MIGRATION_TO_ASPNET10_PLAN.md 40
  6. Gate-Enforced Progression: Progression to subsequent stages is blocked until current stage test gates pass MIGRATION_TO_ASPNET10_PLAN.md 41

Sources: MIGRATION_TO_ASPNET10_PLAN.md 34-42
