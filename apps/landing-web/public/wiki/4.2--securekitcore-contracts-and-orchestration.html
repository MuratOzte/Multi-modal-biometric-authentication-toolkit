The @securekit/core package serves as the foundational shared TypeScript library within the SecureKit monorepo. It establishes the domain models, request/response contracts, biometric signal interfaces, risk evaluation policies, and orchestration logic utilized by both server-side implementations (packages/node-auth, apps/securekit-api) and client-side SDKs (packages/web-sdk).

1. Shared Request and Response Contracts

The core package defines standard data transfer objects (DTOs) and state interfaces for user lifecycle management, challenge issuance, consent verification, and multi-modal profile storage.

Key structural definitions encompass:

  • User Records & Profiles: Standardized schemas for userId, registration timestamps, consent versions, and profile associations (keystroke models, face embeddings, voice references, and card metadata). Identifiers are consistently normalized (trimmed and lowercased where appropriate) across authentication boundaries.
  • Challenges: Structures governing challenge generation, including language parameters (lang), string lengths (length), dynamic word counts (wordCount), and strict time-to-live (CHALLENGE_TTL_SECONDS) constraints.
  • Session Lifecycle: Time-bound session handles (sessionId) tracking expiration windows (SESSION_TTL_SECONDS), accumulated signal states, and evaluation outcomes.

2. Biometrics Modules and Signal Models

Biometric and contextual data are encapsulated into structured signal payloads before being passed to verification services or risk evaluators. The core contracts define uniform schemas for:

  • Keystroke Dynamics: Timings for keydown and keyup events, measuring hold durations and transition latencies to match against Exponential Moving Average (EMA) user profiles or fixed-text templates.
  • Facial and Voice Signals: Embeddings, reference image paths, liveness indicators, and speech-to-text verification payloads evaluated by external Python subprocesses.
  • Network and Location Signals: IP metadata structures containing flags for VPN, proxy, Tor, or relay usage, alongside geographic drift calculations and country-code allowances (allowedCountries).

3. Risk Policies and Default Configuration (defaultPolicy)

The risk policy engine calculates session trust scores and determines whether an authentication attempt is permitted, denied, or requires step-up verification. The defaultPolicy configuration dictates threshold rules and security constraints:

  • Risk Score Bounds: Defines numeric boundaries such as allowMaxRisk and denyMinRisk to categorize aggregated signal scores.
  • Network Enforcement: Parameters like treatVpnAsFailure and minNetworkScore dictate strict denial or penalization when non-residential or proxy IP flags are raised.
  • Step-Up Requirements: Specifies stepUpSteps array mappings, identifying secondary verification modalities (e.g., voice challenge, face re-verification) required when risk scores fall into intermediate bands.
  • Decision Outcomes: Yields discrete resolution values: allow, step_up, or deny for dynamic evaluations, and accept or reject for fixed-text verifications.

4. The Orchestration Engine

The orchestrator coordinates state persistence, incremental signal aggregation, and policy enforcement across an active authentication session.

When a verification request is submitted, the orchestrator executes the following sequence:

  1. Retrieves the active session state from the underlying storage layer (SessionStore).
  2. Appends or merges incoming telemetry signals (signalsUsed) with historical session data.
  3. Invokes the risk evaluation service (SessionRiskEvaluator) against the active policy profile (defaultPolicy).
  4. Generates a unified decision (decision), computes the resulting riskScore, and compiles any required step-up actions (requiredSteps) or diagnostic reasons (reasons).
