This page documents the migration strategy, backend selection environment variables, parity test harnesses, and validation fixtures used to transition from the legacy Node/Express API (packages/node-auth) to the SecureKit ASP.NET Core 10 API (apps/securekit-api). It covers the execution of the aspnet-parity.mjs test runner, the stage-one through stage-seven parity scripts, and the generation of run-logs under .run-logs/.

Backend Selection and Environment Configuration

The monorepo supports running either the legacy Node/Express API or the new ASP.NET Core API behind the Vite development proxy docs/ASPNET_CUTOVER.md 1-31 Backend selection is controlled via environment variables evaluated at startup in the root orchestration scripts and Vite configuration docs/ASPNET_CUTOVER.md 13-23

Configuration Variables

  • VITE_SECUREKIT_API_BACKEND: Controls target selection. Setting this to aspnet routes requests to port 3002, while node routes to port 3001 docs/ASPNET_CUTOVER.md 21-22
  • VITE_SECUREKIT_DEV_PROXY_TARGET: Explicit URL override that takes precedence over VITE_SECUREKIT_API_BACKEND docs/ASPNET_CUTOVER.md 20-21
  • Port defaults: The C# ASP.NET Core API binds to port 3002, the Node/Express API binds to port 3001, and the Vite dev server runs on port 5173 docs/ASPNET_CUTOVER.md 8-10

Stage-One through Seven Parity Scripts

Parity tests are partitioned into seven distinct functional stages covering distinct routing domains and verification boundaries:

  • Stage 1-3: Core authentication contracts, session management, risk evaluation schemas, and challenge stores.
  • Stage 4-6: Biometric routing modules (face embeddings, voice verification, sliding windows, and keystroke profiling).
  • Stage 7: Card verification endpoints, multi-part form handling, reference management, error injection, and Python process bridge behavior packages/node-auth/scripts/stage-seven-parity.ts 1-114

Normalization and Assertion Logic

Because underlying storage paths, system-generated temporary directories, and volatile timestamps (enrolledAt, updatedAt) differ between Node and .NET runtimes, parity scripts normalize responses prior to deep comparison packages/node-auth/scripts/stage-seven-parity.ts 46-57

// Normalization logic mapping volatile paths and dates
const normalize = (value: any, key = ""): any => {
  if (Array.isArray(value)) return value.map(v => normalize(v));
  if (value && typeof value === "object") return Object.fromEntries(Object.entries(value).map(([k, v]) => [k, normalize(v, k)]));
  if (["updatedAt", "enrolledAt", "cardReferenceEnrolledAt"].includes(key)) return "<time>";
  if (typeof value === "string") {
    for (const [name, replacement] of variablePaths) value = value.split(name).join(replacement);
    value = value.replace(/[^\s"']*securekit-card-[^/\\\s"']+[\\/]/g, "<temp>/").replaceAll("\\", "/");
  }
  return value;
};

Fixtures and Deterministic Testing (card-stage7.py)

To ensure parity tests run reliably without requiring local PyTorch, CUDA, or PaddleOCR runtimes, stage seven utilizes a deterministic Python protocol fixture (packages/node-auth/scripts/fixtures/card-stage7.py) packages/node-auth/scripts/fixtures/card-stage7.py 1-53

Protocol Fixture Behavior

The script communicates over stdin/stdout using JSONL protocol frames. It inspects probe image paths to simulate various success and failure conditions without invoking actual machine learning models:

  • timeout: Triggers an intentional 30-second delay to test worker timeout handling packages/node-auth/scripts/fixtures/card-stage7.py 14-15
  • invalid: Emits non-JSON output to test parser error recovery packages/node-auth/scripts/fixtures/card-stage7.py 16-18
  • stdout / stderr: Emits large payload buffers or error streams to validate output draining limits packages/node-auth/scripts/fixtures/card-stage7.py 19-24
  • dependency: Simulates missing python module exceptions (e.g. No module named 'paddleocr') packages/node-auth/scripts/fixtures/card-stage7.py 41-42
